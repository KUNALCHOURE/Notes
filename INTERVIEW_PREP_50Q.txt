SECTION A — PROJECT OVERVIEW & ARCHITECTURE (Q1–Q5)
================================================================================

--------------------------------------------------------------------------------
Q1. Walk me through Medisen in 60 seconds.
--------------------------------------------------------------------------------
A. Medisen is a disease prediction web application. The user selects symptoms
from a searchable dropdown, the React frontend posts them to a Flask backend,
which runs a Random Forest classifier over a dataset of 489 binary symptom
features and 261 disease classes. The model returns probabilities for every
disease; I take the top 5 by probability, look up their associated symptoms
and the relevant medical specialty for each, then join against a Nagpur
doctor dataset to return ranked predictions plus recommended doctors. The
honest accuracy number is around 87% cross-validation. The frontend renders
the top prediction in a primary card and the next four in a shorter list.

--------------------------------------------------------------------------------
Q2. Draw out the system architecture for me.
--------------------------------------------------------------------------------
A. Three layers:

  [React + Vite Frontend]
       |  axios POST { list: ["fever","cough"] }
       v
  [Flask API @ POST /]
       |  predict_top_5_diseases() -> predict_proba() -> argsort top-5
       |  for each disease: give_symptoms() + get_doctors_for_disease()
       v
  [In-memory Random Forest model]      [3 CSVs on disk]
                                         - dis_sym_dataset_comb.csv (training)
                                         - disease_speciality.csv (disease->specialty)
                                         - doctorsfinal_with_mobile.csv (doctors)

There is no database, no message queue, no auth, no caching layer — single
synchronous request/response cycle. That's appropriate for the scope and a
weakness I can defend if asked.

--------------------------------------------------------------------------------
Q3. Why this architecture? Why not put the model on the frontend?
--------------------------------------------------------------------------------
A. Three reasons. One, the model is scikit-learn — Python only, no browser
runtime. Two, the dataset is 8.8 MB; shipping it to every client is wasteful.
Three, keeping the model server-side means I can swap it (RF -> XGBoost -> LLM)
without redeploying the frontend. The trade-off is a network hop per request,
but the model itself runs in milliseconds, so the bottleneck is HTTP, not ML.

--------------------------------------------------------------------------------
Q4. What's the request/response contract?
--------------------------------------------------------------------------------
A. Request: POST / with JSON body { "list": ["fever", "cough"] }.
Response: JSON array of up to 5 items, each:
  {
    "disease": "Influenza",
    "all_symptoms": [...],         # every symptom associated with this disease
    "matched_symptoms": [...],     # subset the user actually selected
    "doctors": [{ "name", "Specialty", "contact", "city" }]
  }
Code references: request parsed at server.py:137, response built at
server.py:154-161.

--------------------------------------------------------------------------------
Q5. Why React + Flask specifically?
--------------------------------------------------------------------------------
A. React for the frontend because the UI is component-based (Search, Result,
ShortDisease, Navbar, Footer) and benefits from declarative state — when the
symptom list changes, useEffect fires the API call automatically. Vite for
sub-second hot reload. Flask for the backend because the model lives in
Python and Flask gives me a single decorator (@app.route) to expose it as an
API — minimal ceremony. For production I'd consider FastAPI for async + free
Pydantic validation, but Flask was the right choice for the scope.

--------------------------------------------------------------------------------
Q6. Describe your dataset.
--------------------------------------------------------------------------------
A. dis_sym_dataset_comb.csv has 8,836 rows (8,835 data + header), 490 columns.
Column 0 is the disease label (label_dis), columns 1-489 are binary symptom
features. There are 261 unique disease classes. Each row represents a case;
each cell is 1 if that symptom is present, 0 otherwise. So the matrix is
mostly sparse — most diseases have only 5-20 active symptoms.

--------------------------------------------------------------------------------
Q7. How do you load and split the data?
--------------------------------------------------------------------------------
A. In server.py:18-22:
  df_comb = pd.read_csv(...)
  X = df_comb.iloc[:, 1:]   # 489 symptom columns
  Y = df_comb.iloc[:, 0]    # disease label column
  x_train, x_test, y_train, y_test = train_test_split(
      X, Y, test_size=0.20, random_state=42
  )
80% train, 20% test, random_state=42 for reproducibility. In the notebook I
used test_size=0.10 because I was iterating fast; 0.20 in production gives
a more stable evaluation.

--------------------------------------------------------------------------------
Q8. Why binary encoding for symptoms?
--------------------------------------------------------------------------------
A. Symptoms are intrinsically boolean (you have it or you don't), and tree-
based models split on equality, so 0/1 is the native format — no scaling, no
normalization, no encoding needed. The downside is information loss: severity
("mild" vs "severe"), duration, and onset order all collapse to "present".
That's a real limitation I'd fix with ordinal encoding (0/1/2/3) for severity.

--------------------------------------------------------------------------------
Q9. How is user input transformed into the model's expected format?
--------------------------------------------------------------------------------
A. server.py:72-77. I build a dict initialized to 0 for every column in
X.columns (all 489 symptoms), then flip selected symptoms to 1, and wrap
the dict in a single-row pandas DataFrame:

  symptoms_dict = {symptom: 0.0 for symptom in X.columns}
  for symptom in symptoms:
      if symptom in symptoms_dict:
          symptoms_dict[symptom] = 1.0
  input_data = pd.DataFrame([symptoms_dict])

Critical detail: building from X.columns guarantees column-order alignment
with what the model was trained on. If you pass features out of order,
sklearn predicts garbage with no error.

--------------------------------------------------------------------------------
Q10. What happens if the user enters a symptom not in your 489 columns?
--------------------------------------------------------------------------------
A. It's silently dropped. The "if symptom in symptoms_dict" check at
server.py:74 skips unknown symptoms. That's a UX problem — the user has no
idea their input was ignored. Production fix: return matched_symptoms and
unmatched_symptoms in the response so the UI can warn. Better fix: use an
LLM or sentence embeddings to map free-text symptoms to canonical names.

--------------------------------------------------------------------------------
Q11. What preprocessing did you do, and what didn't you do?
--------------------------------------------------------------------------------
A. Did: nothing beyond split — because the data is already binary, in the
right shape, and column-aligned. Didn't: check for missing values, check
for duplicate rows, check for all-zero columns (low-variance noise),
apply class_weight for imbalance, or stratify the split. Stratifying with
stratify=Y is the highest-leverage fix because 261 classes with random
split means rare diseases can be absent from train or test.

--------------------------------------------------------------------------------
Q12. Is 8,835 rows enough data?
--------------------------------------------------------------------------------
A. Marginal. 8,835 / 261 = ~34 rows per disease. For a clean tabular
classification problem with good features, 30+ per class is workable, which
is why I'm getting 87% CV. For production medical use I'd want 100+ per
class and clinician validation of every disease-symptom mapping.

SECTION C — MACHINE LEARNING DEEP DIVE (Q13–Q25)
================================================================================

--------------------------------------------------------------------------------
Q13. Why Random Forest? What did you compare it against?
--------------------------------------------------------------------------------
A. In notebook I trained RF, KNN, and Decision Tree on the same data:
  RF:  90.50% test / 87.04% 5-fold CV
  KNN: 91.06% test / 85.25% CV
  DT:  90.95% test / 83.67% CV

KNN had marginally higher test accuracy but the lower CV tells the real
story — it was overfitting that specific split. RF won on the metric that
generalizes. RF also handles high-dimensional binary data well, captures
symptom interactions through tree splits, and gives me predict_proba for
free, which I need for the top-5 feature.

--------------------------------------------------------------------------------
Q14. Explain how Random Forest works internally.
--------------------------------------------------------------------------------
A. Two layers of randomness:

  1. Bagging (bootstrap aggregation): For each of N trees, sample the
     training set with replacement to get a different subset. Each tree
     sees a slightly different view of the data.

  2. Feature subsampling: At every split inside every tree, instead of
     considering all 489 symptom columns, only consider a random subset
     (sklearn default is sqrt(n_features) ~= 22 for our data).

Each tree votes. predict() returns the majority vote. predict_proba()
averages the per-tree class probabilities. The two layers of randomness
decorrelate the trees, so they make different mistakes — and averaging
uncorrelated errors is exactly how you reduce variance.

--------------------------------------------------------------------------------
Q15. What is bagging vs boosting?
--------------------------------------------------------------------------------
A. Bagging (Random Forest):
  - Trees trained in parallel on bootstrap samples
  - Predictions averaged
  - Reduces variance
  - Hard to overfit
  - Each tree is a "weak" learner that becomes strong via averaging

Boosting (XGBoost, LightGBM, AdaBoost):
  - Trees trained sequentially
  - Each new tree corrects the previous tree's errors (focuses on residuals)
  - Reduces bias
  - Easier to overfit, harder to tune
  - Often higher peak accuracy on tabular data

I used bagging because it's robust with minimal tuning. For a v2 I'd try
XGBoost — typically beats RF by a few points on tabular data.

--------------------------------------------------------------------------------
Q16. What do n_estimators=100 and criterion='entropy' mean?
--------------------------------------------------------------------------------
A. n_estimators=100 means the forest has 100 decision trees. More trees =
more stable predictions, with diminishing returns past ~100-200. In the
notebook I used 10 for fast experimentation; in server.py:24 I bumped to
100 for production.

criterion='entropy' (used in the notebook) means tree splits are chosen to
maximize information gain, where impurity = -sum(p * log(p)) — Shannon
entropy. The alternative is 'gini' (sklearn default) = 1 - sum(p^2). Both
give nearly identical accuracy; gini is slightly faster because no log.

--------------------------------------------------------------------------------
Q17. What does train_test_split do and why 80/20?
--------------------------------------------------------------------------------
A. train_test_split shuffles the data and partitions it. With 8,800 rows,
20% test = ~1,770 rows — large enough for a stable estimate, leaving 7,000
to train on. The random_state=42 makes the split reproducible across runs.

Why not 90/10? With 261 classes, a 10% test set means ~3 samples per class
on average — too small for per-class metrics to mean anything.

Should I have used stratify=Y? Yes. Without stratification, the random
split can leave rare diseases entirely out of train or test, biasing
evaluation.

--------------------------------------------------------------------------------
Q18. What is cross-validation and why use cv=5?
--------------------------------------------------------------------------------
A. 5-fold CV splits the data into 5 equal folds, trains on 4, tests on
the 5th, rotates through all 5 folds, averages the accuracy. It gives a
much more reliable generalization estimate than a single train/test split
because it averages over 5 different test sets.

My RF: 90.5% single-split test accuracy, 87.04% 5-fold CV. The 87 is the
honest number — single-split accuracy is noisy and partly random.

cv=5 is the standard default — good balance between reliability (10 would
be better but 2x slower) and speed.

--------------------------------------------------------------------------------
Q19. How does predict_proba work in Random Forest?
--------------------------------------------------------------------------------
A. For each tree:
  - The input traverses the tree based on feature splits
  - Lands in a leaf
  - The leaf has a class distribution from the training data that ended up
    there (e.g., 80% Influenza, 15% Pneumonia, 5% Cold)
  - That distribution is the tree's predicted probability

The forest's probability is the average across all 100 trees. predict_proba
returns a 1x261 array — one probability per disease class. This is what
makes the top-5 feature possible.

--------------------------------------------------------------------------------
Q20. Walk me through your top-5 prediction code.
--------------------------------------------------------------------------------
A. server.py:79-81:

  probabilities = random_forest.predict_proba(input_data)
  top_indices = probabilities.argsort()[0][-5:][::-1]
  return [random_forest.classes_[i] for i in top_indices]

Step by step:
  1. predict_proba returns shape (1, 261) — probabilities for every class
  2. argsort returns the indices that would sort the array ascending
  3. [0] takes the single row (we passed one sample)
  4. [-5:] takes the last 5 indices = the 5 highest probabilities
  5. [::-1] reverses so highest comes first
  6. random_forest.classes_ maps indices back to disease names

This is a clean idiom — no manual sorting, vectorized via numpy.

--------------------------------------------------------------------------------
Q21. What is overfitting? How do you detect and prevent it?
--------------------------------------------------------------------------------
A. Overfitting = model memorizes training data including noise; performs
well on training, badly on unseen data.

Detection: gap between training accuracy and CV accuracy. My RF training
accuracy is effectively 100% because trees can memorize, but CV is 87% —
that gap is normal and acceptable for bagging.

Prevention in RF:
  - Bootstrap sampling decorrelates trees
  - Feature subsampling forces diversity
  - Averaging reduces variance
  - Hyperparameters: max_depth (limit tree depth), min_samples_leaf
    (require minimum samples per leaf), max_features (stronger subsampling)

I imported GridSearchCV in the notebook but didn't run it — be honest if
asked. Tuning max_depth would be the first thing I'd try.

--------------------------------------------------------------------------------
Q22. What is feature importance and how does it work in RF?
--------------------------------------------------------------------------------
A. For each feature, sum the impurity reduction across every split that
used that feature, weighted by how many samples that split affected, then
average across all 100 trees. sklearn exposes it as
random_forest.feature_importances_ — a 489-element array summing to 1.

Higher value = more discriminative. I'd expect symptoms like "jaundice"
(narrows to liver/biliary) or "rash" (narrows to skin/infectious) to score
high, while generic symptoms like "fever" or "pain" score lower because
they appear across many diseases.

I don't expose this in the app — should have. Easy fix: serialize
feature_importances_ alongside the model, expose via an /explain endpoint.

--------------------------------------------------------------------------------
Q23. Is your 87% accuracy good enough for medical use?
--------------------------------------------------------------------------------
A. No — and this is the answer that impresses interviewers. 87% means
1 in 8 predictions is wrong. With 261 classes, accuracy also hides
class imbalance: high accuracy could mean the model is great on common
diseases and terrible on rare ones. In medicine, false negatives are
catastrophic.

That's why Medisen is positioned as a TRIAGE TOOL, not a diagnostic system.
It returns the top-5 so even if #1 is wrong, the right answer is likely in
the shortlist. The scrolling disclaimer at Search.jsx:251 makes this
explicit. For real medical deployment I'd need:
  - Per-class precision/recall, not just accuracy
  - Clinician validation
  - High-recall calibration for serious conditions
  - Regulatory pathway (FDA SaMD / CDSCO)

--------------------------------------------------------------------------------
Q24. Why don't you compute precision/recall/F1?
--------------------------------------------------------------------------------
A. Honest answer: I only used accuracy_score (server.py:28) because I was
iterating fast and the dataset has 261 classes — eyeballing a 261x261
confusion matrix during dev wasn't realistic.

The fix is one line: classification_report(y_test, rf_pred) from sklearn
gives per-class precision, recall, F1, and support. The headline metric
I'd report is macro-F1 — it treats every class equally regardless of
support, which is the right thing for imbalanced multi-class problems.

--------------------------------------------------------------------------------
Q25. How would you handle class imbalance?
--------------------------------------------------------------------------------
A. Three options, ranked by effort:
  1. class_weight='balanced' on RandomForestClassifier — one parameter,
     weights classes inversely by frequency.
  2. stratify=Y in train_test_split — ensures train and test have
     proportional class representation.
  3. SMOTE for synthetic minority oversampling — but risky for binary
     features because it creates non-integer synthetic rows.

I'd start with (1) and (2) — both are essentially free.

Q31. What's the difference between Flask and FastAPI?
--------------------------------------------------------------------------------
A. Flask: synchronous WSGI, minimal core, manual everything (validation,
docs, async). Mature, widely deployed.

FastAPI: asynchronous ASGI, built on Starlette + Pydantic, auto-generated
OpenAPI/Swagger docs, native type-hint validation, async/await support.
Faster for IO-bound workloads.

For a single-endpoint ML serving app, Flask is fine and familiar. For a
larger API with validation, docs, and async needs, FastAPI is the better
default in 2025.

Q32. What's a REST API? Is your API RESTful?
--------------------------------------------------------------------------------
A. REST = Representational State Transfer. Core principles:
  - Resources identified by URLs
  - HTTP verbs map to operations (GET, POST, PUT, DELETE)
  - Stateless — server doesn't store client state between requests

Is mine RESTful? Mostly. POST / accepts symptoms, returns predictions.

SECTION F — EVALUATION & METRICS (Q39–Q42)

--------------------------------------------------------------------------------
Q39. What's the difference between accuracy, precision, recall, and F1?
--------------------------------------------------------------------------------
A. For a binary problem (extend per-class for multi-class):

  Accuracy  = (TP + TN) / (TP + TN + FP + FN)
              "Of all predictions, how many were right?"
  Precision = TP / (TP + FP)
              "Of the times I said YES, how many were actually YES?"
              Controls false positives.
  Recall    = TP / (TP + FN)
              "Of all actual YES cases, how many did I catch?"
              Controls false negatives.
  F1        = 2 * (P * R) / (P + R)
              Harmonic mean — penalizes imbalance between P and R.

For medical: recall matters more than precision because false negatives
(missing a disease) are worse than false positives (over-suggesting).

--------------------------------------------------------------------------------
Q40. What is a confusion matrix?
--------------------------------------------------------------------------------
A. An NxN grid where cell (i, j) is the count of times class i was
predicted as class j. Diagonal = correct predictions; off-diagonals =
errors. For 261 classes mine would be 261x261 — too big to eyeball, but
visualized as a heatmap it surfaces which disease pairs the model
confuses (e.g., common cold vs flu).

Computing: sklearn.metrics.confusion_matrix(y_test, y_pred). Plotting:
seaborn.heatmap.

--------------------------------------------------------------------------------
Q41. Why do you report CV accuracy instead of test accuracy?
--------------------------------------------------------------------------------
A. CV averages over 5 different train/test splits. Single test accuracy
is noisy — one specific random_state can get lucky or unlucky.
  My single-split test accuracy: 90.5%
  My 5-fold CV accuracy:        87.04%

The 3-point gap is the noise that CV averages out. 87 is the honest
generalization estimate. Always trust CV over a single split.

--------------------------------------------------------------------------------
Q42. What's the bias-variance trade-off?
--------------------------------------------------------------------------------
A. Bias: error from wrong assumptions (model too simple to capture the
pattern). High bias = underfitting.
Variance: error from sensitivity to small data changes. High variance =
overfitting.

Trade-off: simple models (linear regression, shallow trees) = high bias,
low variance. Complex models (deep nets, deep trees) = low bias, high
variance.

Random Forest's trick: each tree is high-variance (low bias, deep, overfit
to its bootstrap sample), but averaging 100 of them collapses variance
without raising bias. That's the entire reason ensembles work.

SECTION G — MODERN AI / LLM / RAG / AGENTS (Q43–Q47)

--------------------------------------------------------------------------------
Q43. Could you replace your Random Forest with an LLM?
--------------------------------------------------------------------------------
A. Yes but you shouldn't, and here's why — this is the nuance that
impresses Ace interviewers.

My data is structured, tabular, binary — exactly the format where tree
ensembles dominate. An LLM is a statistical text predictor; passing a
489-dim binary vector as text is lossy. Worse, the LLM doesn't know my
dataset's distribution — it has the internet's. It would over-weight
famous symptom-disease associations like "chest pain -> heart attack"
because that's the cultural trope, when my dataset might statistically
support a different diagnosis.

Tree ensembles also give me CALIBRATED PROBABILITIES via predict_proba —
something LLMs don't natively expose. So for the prediction step, RF is
strictly better.

The RIGHT pattern is hybrid:
  User free text -> LLM (extract symptoms) -> RF (predict) -> LLM (explain)

--------------------------------------------------------------------------------
Q44. What is RAG and how would you use it here?
--------------------------------------------------------------------------------
A. RAG = Retrieval-Augmented Generation. Instead of asking an LLM to
recall facts (which it hallucinates), you:
  1. Index a trusted corpus into a vector database (embeddings).
  2. At query time, embed the query, retrieve top-k similar chunks.
  3. Pass those chunks as context to the LLM along with the question.
  4. Force the LLM to answer only using the retrieved context (cite or
     refuse).

For Medisen:
  - Knowledge base: PubMed abstracts, MedlinePlus articles, Mayo Clinic
    symptom pages, ICD-10 disease descriptions.
  - Embedding model: Voyage AI, Cohere, or OpenAI text-embedding-3-small.
  - Vector store: pgvector (Postgres extension), Pinecone, Weaviate, or
    MongoDB Atlas Vector Search.
  - Flow: RF predicts top-5 diseases -> for each, retrieve top-3 medical
    chunks -> LLM generates "We predicted Influenza because your fever +
    body ache + fatigue matches [source: Mayo Clinic]."

The LLM's job is NOT prediction — it's grounded explanation.

--------------------------------------------------------------------------------
Q45. What is an agentic workflow? Design one for Medisen.
--------------------------------------------------------------------------------
A. An agent is an LLM in a loop with tools. It can decide which tool to
call, observe the result, and call another tool, until it produces a
final answer.

Medisen agent loop:
  1. extract_symptoms(user_text) — LLM parses natural language to
     canonical symptoms.
  2. predict_diseases(symptoms) — calls my RF API.
  3. If top-1 RF probability < 60%:
       clarify(symptoms) — LLM asks a follow-up question
       ("Is the chest pain sharp or dull?"), then back to step 1 with
       new info.
     Else continue.
  4. retrieve_medical_context(disease) — RAG over the medical corpus.
  5. find_doctor(disease) — existing specialty -> doctor logic.
  6. Final synthesis: LLM generates an explanation with citations and
     recommended doctors.

The killer feature is step 3 — confidence-driven clarification. That's
how doctors actually triage: ask, refine, repeat.

Framework: LangGraph, OpenAI's Assistants API, or Anthropic's tool use
in the Messages API.

--------------------------------------------------------------------------------
Q46. How do you prevent hallucination in a medical AI app?
--------------------------------------------------------------------------------
A. Five layers:

  1. Ground in retrieval (RAG): model can only state facts present in
     retrieved chunks.
  2. Cite-or-refuse: if no citation available for a claim, the model
     must say "I don't have evidence for this."
  3. Structured outputs: enforce JSON schemas so the model can't invent
     fields. Use response_format / function calling.
  4. Low temperature: 0.0-0.2 for medical content — minimize creative
     deviation.
  5. Post-hoc fact-checker: a second model or rule-based check that
     verifies each medical claim against the source corpus before
     showing it to the user.

Plus product-level guardrails: always-on disclaimer, escalation paths
for emergency symptoms ("chest pain + sweating + arm pain -> call
emergency immediately, bypass the model"), audit logging.

Q47. What's prompt engineering? Show me a prompt you'd write.
--------------------------------------------------------------------------------
A. Prompt engineering = designing the input to an LLM so the output is
reliable, structured, and grounded. Key tactics:
  - System prompt with explicit role and constraints
  - Few-shot examples
  - Strict output format (JSON schema)
  - Low temperature for deterministic tasks

For the Medisen symptom extraction step:

  SYSTEM:
  You are a medical NLP assistant. Extract symptoms from the user's
  description and map each to the closest match in the provided
  vocabulary. Return JSON only. If a symptom doesn't match, list it
  under "unmatched". Do not invent symptoms not stated by the user.

  VOCABULARY:
  [abdominal cramp, abdominal distention, ..., shortness breath, ...]

  USER:
  "I've been having a tight chest and trouble breathing for two days."

  OUTPUT FORMAT:
  {
    "extracted": [
      {"text": "tight chest", "canonical": "chest pain", "confidence": 0.85},
      {"text": "trouble breathing", "canonical": "shortness breath", "confidence": 0.95}
    ],
    "unmatched": []
  }

Set temperature=0.1, max_tokens limited, response_format=json_object.

A. Honest answer — the model isn't clinically validated. The dataset is

Q49. What was your hardest technical challenge?
--------------------------------------------------------------------------------
A. Aligning user input to the model's expected feature order. The model
was trained on a specific column order (489 symptoms in a specific
sequence). If I pass a feature vector with even one column swapped,
sklearn doesn't error — it silently predicts garbage.

Solution at server.py:72-77: build the input dict from X.columns itself,
not from a hardcoded list. That guarantees the column order matches what
the model expects:

  symptoms_dict = {symptom: 0.0 for symptom in X.columns}
  for symptom in symptoms:
      if symptom in symptoms_dict:
          symptoms_dict[symptom] = 1.0
  input_data = pd.DataFrame([symptoms_dict])

Lesson: trust the model's source-of-truth (X.columns) for feature order,
not your own assumptions. This is a common silent-failure mode in
production ML.

================================================================================
                              GLOSSARY — DRILL THESE
================================================================================
  Bagging:           Bootstrap Aggregating — train on resamples, average.
  Boosting:          Sequential trees, each correcting prior errors.
  Bootstrap sample:  Random sample with replacement, same size as original.
  Class imbalance:   Some classes have many more samples than others.
  Confusion matrix:  Grid of predicted vs actual class counts.
  Cross-validation:  Train on k-1 folds, test on 1, rotate, average.
  Entropy:           -sum(p * log p), measure of impurity.
  F1 score:          Harmonic mean of precision and recall.
  Feature importance: How much each feature reduces impurity across trees.
  Gini impurity:     1 - sum(p^2), alternative impurity measure.
  Hallucination:     LLM generating false but plausible-sounding facts.
  Information gain:  Reduction in entropy from a split.
  Overfitting:       Model memorizes train data, fails on new data.
  predict_proba:     Returns per-class probabilities, not just one label.
  Precision:         TP / (TP + FP).
  Random Forest:     Ensemble of decision trees with bagging + feature
                     subsampling.
  Recall:            TP / (TP + FN).
  RAG:               Retrieval-Augmented Generation — ground LLM output in
                     retrieved corpus.
  Stratified split:  Train/test split preserves class proportions.
  Top-k:             Return the k highest-probability classes.
